# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ModCon HR is a modern HRMS single-page app (React + TypeScript + Vite + Tailwind), backed by Firebase (Auth + Firestore) and hosted on Vercel at `modcon-hr.vercel.app`. **Firebase is backend and database only — never the host.** Firebase Hosting is not used and `firebase deploy --only hosting` must not be run.

## Commands

```bash
npm run dev        # Vite dev server → http://localhost:5173
npm run build      # tsc -b && vite build  (type-check is part of the build)
npm run preview    # serve the production build locally
npm run test:e2e   # Playwright E2E (playwright test)
npm run test:rules # Firestore security-rules tests (Firestore emulator; needs Java)
```

- **Type checking is the CI gate, not lint.** `npm run lint` (`eslint .`) is defined but ESLint is **not configured or installed**, so it currently fails. Correctness is enforced by `tsc -b` inside `npm run build` — run the build to type-check.
- **Tests run against emulators, never the live project.** `npm run test:e2e` points the bundle *and* the specs' REST helpers at the Firestore (`:8080`) and Auth (`:9099`) emulators, and [scripts/e2e.sh](scripts/e2e.sh) starts them if nothing is listening. `npm run test:rules` was always emulator-only. **Nothing needs to run against the live project.** The one thing an emulator cannot tell you — whether *production* is running these rules — is answered by `npm run rules:verify`, which fetches the deployed ruleset from the Firebase Rules API and compares it byte-for-byte with `firestore.rules`. It reads no documents and spends no Firestore quota. When it passes, an emulated run covers the deployed rules; when it fails, deploy rather than test live. There is deliberately **no npm script that runs against the live project** — reaching it means typing `E2E_LIVE_FIRESTORE=true` by hand, and it writes the organisation's real data. A live matrix run on 2026-08-03 exhausted the project's daily Firestore quota, which then refused every read and write for the rest of the day — the app stopped saving, and four fake `E2E Isolation Leave` policies were stranded in Settings for every employee to see, un-removable because removing them needed the quota the run had spent.
- **Single E2E test / project:** `npx playwright test tests/e2e/smoke.spec.ts`, filter with `-g "test name"`, or one role with `--project=role-admin`. Point at the sandbox browser with `PW_CHROMIUM_PATH=/opt/pw-browsers/chromium` (Chromium only — the other engines use their own downloaded builds). The suite builds + serves the production bundle and signs in against the **Auth emulator**, so it needs no network access to Firebase and no live credentials.
- **The app specs run on all three engines; scope with `E2E_BROWSERS`.** `E2E_BROWSERS=chromium npm run test:e2e` is the fast Chromium-only run. Firefox/WebKit need their browsers downloaded once via `npx playwright install firefox webkit`.
- **Security rules are tested separately from the app.** `tests/rules/` runs `firestore.rules` against the Firestore emulator via `@firebase/rules-unit-testing` (`npm run test:rules`, wrapped in `firebase emulators:exec`; needs a JDK). The E2E suite drives the UI and never exercises the rules, so role/permission changes need a test here as well. Each test reseeds — the suites mutate roles, so shared state produces false passes.
- **CI:** `.github/workflows/ci.yml` runs the build, the rules tests **and the E2E suite** (`app` + `org-settings`, Chromium only) on every pull request and push to `main`. Nothing in CI touches the live project — Firestore and Auth are emulated, and the `e2e` job refuses to start if `E2E_LIVE_FIRESTORE` is set, however it got there. `npm run test:unit` is *not* in CI yet; it is the pure-arithmetic suite (`src/data/shiftRules.ts`, `src/data/geofenceRules.ts`) and runs in about a second, so adding it is free.
- **Deploy:** the app ships via **Vercel's Git integration** — pushes to `main` build and promote to production, pull requests get preview URLs. There is no deploy workflow in this repo; build settings live in `vercel.json`. Manual deploy from a checkout: `npx vercel --prod`. Firestore rules deploy separately through Firebase: `npm run rules:deploy` (`firebase deploy --only firestore:rules`). **App code and rules deploy independently — if a change needs both, deploy the rules first or privileged users get permission-denied against the new UI.**

Path alias: `@/*` → `src/*` (configured in both `tsconfig.json` and `vite.config.ts`).

## Architecture

### Mutable collections are the organisation's, not the browser's

Anything a user can change goes through `persistentCollection` in `src/data/persistence.ts`, which is **Firestore-backed with localStorage as its cache** — the same arrangement `lib/orgSettings.ts` uses for configuration, and for the same reason: data modules read synchronously at module-load time, before React or auth resolves, so they cannot await. Full design in [docs/shared-records-spec.md](docs/shared-records-spec.md).

- **It used to be localStorage and nothing else**, which meant two people in one company saw two unrelated datasets — an employee checked in on their phone and HR, on a laptop, saw nothing — and a cleared cache was unrecoverable data loss with no backup. Invisible from the screens, because a demo is one person in one browser, and invisible to the E2E suite, because every spec ran in a single context where per-browser and shared storage are indistinguishable. `tests/e2e/shared-records.spec.ts` uses **two browser contexts** and is the only spec that can tell them apart.
- **Firestore holds only what differs from the seed**, plus a tombstone for a deleted seed record; `get()` merges. Materialising the demo dataset into every new organisation would cost hundreds of documents to say nothing the code already says. Tombstones are not optional — absence cannot distinguish "removed" from "never there", so without one a deleted record reappears.
- **One collection, `org_records`**, keyed `<orgKey>__<store>__<recordId>` with the record as a JSON string in `data`: one rules block rather than nine. `employeeId` and `status` are lifted to top-level because rules cannot parse the JSON and "only a manager decides a leave request" has to be expressible.
- **The rules are a tenant boundary plus one authority rule** (an employee cannot move a leave request out of `Pending`). They are *not* yet a per-record authority boundary — whether a ticket is edited by its owner is still client-side. See §5 of the spec before adding a store; do not widen the generic block.
- **Stores register late, and the sync accounts for it.** Every page is `React.lazy`-loaded, so `src/data/assets.ts` is not imported until somebody opens Assets — long after `startSharedCollectionsSync` ran. A registry read once at sync time subscribes to whichever modules happened to be loaded and silently leaves the rest per-browser. `activeOrgKey` outlives the call so a late registration subscribes itself.
- **Writes are optimistic, and a reload is not free.** `save()` writes the cache, fires the change event and returns; the commit follows and is never awaited. A reload is a *fresh Firestore SDK with an empty mutation queue*, so an un-acked write does not survive the page that made it — the new page subscribes, the server sends the older copy, and `hydrate` writes it over the cache. The change reverts, and it looks exactly like a decision that never landed. The same race runs the other way for a reset: a delete issued before the commit is overtaken by it. Specs therefore wait — `waitForOrgRecord` where they can state the expected value, `waitForOrgRecordsQuiet` where they cannot (two identical reads 400 ms apart; one read a moment after a click sees the state *before* it just as convincingly). Enabling Firestore's `persistentLocalCache` would remove the hazard rather than wait it out, and is not done: the E2E resets clear `localStorage`, not IndexedDB. See §9 of the spec.
- **A page that seeds `useState` from a store must now re-read on its change event.** That pattern was safe while the store was this browser's; a colleague's write now arrives through the subscription and a mount snapshot never sees it. Assets, Helpdesk, Expenses and the leave approvals page were each fixed this way — the two-browser spec is what caught it. **Read it through the store's getter everywhere, never the exported seed array.** Aggregates (`src/data/dashboard.ts`, `src/data/notifications.ts`) and the approval pages all derived from the seeds, so a decision made on one page left every other surface reporting its original figure. `src/lib/seed.ts` is the deliberate exception — it pushes the canonical demo dataset into Firestore. Components that stay mounted while data changes elsewhere subscribe via `useDashboardDataRevision` / `useCollectionRevision`. Seeding `useState` straight from a `src/data/*.ts` array means every edit is lost on refresh, which is what attendance, assets, expenses, helpdesk and payroll all did. `tests/e2e/persistence.spec.ts` guards this: it creates a record, **reloads**, and asserts it survived. The other specs never reload, so in-memory state passes them exactly as persisted state would.

### The Board is the organisation's feed, and it is real

`/board` ([src/pages/feed](src/pages/feed/index.tsx), `src/lib/orgFeed.ts`, Firestore `org_posts`) replaces `announcements` in `src/data/common.ts` — a static array, read-only, identical for every tenant, impossible for anyone inside a company to add to. Firestore-native from the first line rather than another overlay to migrate later.

- **Reactions are a `uid → emoji` map on the post, and that is a rules decision.** It lets `firestore.rules` require that an update's diff touches only `[request.auth.uid]` — so "you may react as yourself and nobody else" is a property of the storage rather than of the button. A counter would let anyone increment anything. The emoji set is closed and mirrored in the rules.
- **Every update path is restricted to the keys it is about**, so "react" cannot double as "rewrite what this post says". `tests/rules/org-posts.rules.test.mjs` has the test for that specific smuggle, and for reply immutability — a conversation people rely on is not one where earlier turns change under later ones.
- **Celebrations are derived, never stored** ([src/data/celebrations.ts](src/data/celebrations.ts)): birthdays and anniversaries from `dateOfBirth`/`dateOfJoining`, compared in IST. A post per celebration would need a scheduled job this project has no backend for. The board offers a composer pre-filled with a greeting instead, so the wish is a real post by a real person. Resigned employees and zero-year anniversaries are excluded; 29 February is not substituted.
- **Deliberately not in the permission matrix.** A noticeboard an administrator can switch off for employees is one nobody reads, so `NavItem.module` is optional and the filter in `nav.ts` says so.

### Four data sources — do not conflate them

1. **Mock/seed data in `src/data/*.ts`** powers most feature pages (attendance, leave, payroll, etc.). It is static seed data, not Firestore.
2. **The employee directory is a mutable localStorage-backed overlay.** `getEmployeeDirectory()` (`src/data/employees.ts`) merges seed employees + locally-added employees minus locally-deleted IDs (both persisted in localStorage). `addEmployeeToDirectory` / `deleteEmployeeFromDirectory` mutate it and dispatch a `modcon-hr-directory-changed` window event; components (e.g. `Topbar`) listen and re-render. So `employees` / `getEmployee(id)` reflect live local edits, **not** the raw seed array.
3. **A separate live Firestore layer** (`src/lib/db.ts` typed collection refs + `src/lib/useFirestore.ts` real-time `use*()` hooks like `useEmployees`, `useExpenses`). This is currently used mainly by the **Admin dashboard**. `useEmployees()` (Firestore) and `@/data/employees` (mock directory) are two different employee sources — pick deliberately.
4. **Organisation configuration is Firestore-backed, and localStorage is its cache.** Leave policies, company profile, holidays, departments, work locations, the salary structure, the permission matrix and the notification/integration preferences live in `org_settings` (one document per setting per org, keyed `<orgKey>__<setting>`). `src/lib/orgSettings.ts` holds the registry, publishes on save, and subscribes at sign-in to hydrate the same localStorage keys the data modules already read synchronously at module-load time. **A new configuration surface goes in that registry, not in a bare localStorage key** — held locally it is invisible to the organisation's other administrators, and leave accrual is what payroll deductions are computed from. See [docs/tenant-isolation-spec.md](docs/tenant-isolation-spec.md) §3.4.

### Departments and locations are both org configuration

Add Employee offers "+ Add new…" for each, and both land in `org_settings` so the next administrator is offered them too. HR can do this — `Employee Directory` is `full` for HR Manager in the permission matrix, and `org_settings` writes need `isOrgAdmin()`, which HR is.

- **Locations were derived, and that read as working.** `syncDirectorySnapshots` collected the distinct `location` of everyone in the directory, so typing a new one and saving made it appear — in that browser only, because the directory is localStorage, and only until its last occupant moved. An office is not a property of the people in it. Declared locations now live in `ORG_SETTINGS.customLocations` ([src/data/locations.ts](src/data/locations.ts)) and the list the app shows is `mergeLocations(derived)` — declared ∪ where people actually are, so nothing needed migrating.
- **Both creation points declare it**: `ensureLocation` in Add Employee and `createLocation` on the profile's inline editor. Adding one without declaring it is the old behaviour, silently.
- **Reporting manager is the live directory** (`employeeOptions={employeeList}`), so somebody hired a moment ago is selectable as a manager immediately — **and one who is not there yet can be added**. Both places that name a manager offer it: "+ Add new reporting manager…" in Add Employee, and "+ Add new manager…" in the profile's Reporting Manager row.
  - **A manager is an employee, so they are asked for in full** — the same fields, the same rules, one `useEmployeeDetailsForm` used twice. A manager captured as a name alone showed "—" across their own profile and ₹0 in payroll, which is what the first attempt at this did and why it was reverted.
  - **Add Employee creates nobody until Save**, the rule the new-department field follows: the manager is held as `newManager` on the payload, `PENDING_MANAGER` stands in for their id, and abandoning the dialog leaves nobody behind. On the profile there is nothing to hold it against, so that dialog creates and assigns as one act.
  - **Two unsaved people can collide on one employee code and the directory cannot see it.** Both drafts open on the same suggestion (`suggestEmployeeCode(directory, ahead)` offers the manager the next one), and `sameEmployeeCode` refuses a manager sharing the hire's — everything that matches a person by their code would otherwise name two people and refuse.
  - **The manager's own manager comes from the directory, never a further new person**, which would recurse with nothing to stop it — and on a profile it is the same cycle-free set the picker offers, so the new manager cannot end up reporting to somebody who reports to them.
  - **`createEmployeeFromDetails` is the one way a person is created**, because a second copy is a second chance to omit the account link — which fails closed and silently: without it `firestore.rules` resolves that account to no employee and they read none of their own salary or leave.
  - `tests/e2e/reporting-manager.spec.ts` is the guard, in the app projects, and it counts `modcon.hr.customEmployees` rather than reading the page — the failure worth catching is a dialog for one person quietly adding two, or none.
- **Settings → Locations manages them.** Declared locations can be renamed — which moves everyone posted there with them, or they would sit at a name the organisation no longer offers — or withdrawn, but only once nobody is there. Inferred locations (a place that exists only because somebody's record says so) get no buttons: there is no declaration to edit, and they stop being offered on their own when the last person moves.
- `tests/e2e/location-directory.spec.ts` is the guard, in the org-settings project because it writes shared configuration. It asserts against the organisation's Firestore copy and then from a **second browser context** — a reload proves nothing here, since the cache reloads with it, and that second context is also a browser where nobody is posted at the new location.

### The salary split is the organisation's, not the platform's

How a monthly gross becomes Basic, HRA, Medical Allowance, Conveyance Allowance and Special Allowance is per-organisation configuration (Settings → Salary Structure, [src/data/salaryStructure.ts](src/data/salaryStructure.ts), registered in `ORG_SETTINGS`).

- **There is no platform default, and an unset structure shows nothing.** `getSalaryStructure()` returns `null` for an organisation that has not configured one, `buildPayslipComponents` reports `splitConfigured: false` with every component at zero, and each surface renders "not set" instead of a breakdown. Falling back to a plausible Basic 50% would tell a company its pay is divided in a way nobody there decided. Basic 50 / HRA 25 / ₹1,492 is **ModCon Builders' demo data**, gated by `isMockDataCleared()` exactly like `demoCompanyProfile` — the demo org shows it, a real organisation created later does not.
- **Gross and net never depend on the split.** `grossEarnings` is CTC ÷ 12 and net is that minus unpaid absence, so an unconfigured organisation still sees correct pay; only the component rows are withheld.

- **`splitMonthlyGross(monthly, structure)` is the one definition of the arithmetic.** `buildPayslipComponents` computes payslips with it and the Settings preview shows an unsaved change with it; written twice, the preview would eventually promise a split the payslip does not pay.
- **Special Allowance is never configured — it is the remainder**, so the components always sum to the monthly gross including the rupee or two that rounding Basic and HRA leaves behind. The flat allowances are capped by what is left after the percentages, or a low enough salary yields a negative Special Allowance.
- **Read it through `getSalaryStructure()` at call time**, never captured at module load, and subscribe with `useSalaryStructureRevision` in anything that stays mounted — an administrator can change it in Settings, and the cache is hydrated from Firestore after sign-in.

**An individual's split can differ, and HR uploads those.** Settings → Salary Structure → *Custom splits for individual employees* takes a CSV (`employee_code,basic_percent,hra_percent,medical_allowance,conveyance_allowance`), stored in `ORG_SETTINGS.employeeSalaryStructures` beside the organisation's own and sharing its change event.

- **`getSalaryStructureFor(employeeId)` is what payroll asks**, not `getSalaryStructure()`. It answers "the split this person is paid on" — theirs where one exists, the organisation's otherwise, `null` when neither does, so an unset organisation still shows "not set" rather than a default. `getSalaryStructure()` goes on meaning "what this organisation splits a gross on", which is what Settings edits and what everyone without an exception is paid on. Passing no id is exactly that.
- **A row carries the whole split — all four figures, every time.** The opposite of the per-employee *leave* policies, which are sparse, and deliberately: these four numbers are not independent (Basic and HRA cap each other, the flat allowances are capped by what those leave, Special Allowance is the remainder). Three of somebody's own numbers beside one of the company's is a structure nobody negotiated, so a partial row is refused rather than completed from the organisation's.
- **The cost of storing it whole is that an individual's split does not follow a later change to the organisation's.** That is what "custom" means here; the Settings list names everyone it is true of, and removing an exception puts them back on the organisation's structure rather than on nothing.
- **A row that cannot be used is reported, never dropped** — the same rule as the payslip and leave-entitlement uploads. A line silently ignored looks exactly like a line applied, while the person it named goes on being paid on the organisation's split. `Basic + HRA > 100` is refused rather than clamped: `normalizeSalaryStructure` would quietly shrink HRA to fit, and the review list would then show figures HR never typed.
- **Every salary-split assertion lives in `tests/e2e/salary-structure.spec.ts`**, one `describe.serial` in the org-settings project. Two spec files would run in different workers against one emulator and each would see the other's half-applied state — which is exactly what makes "clear it, then check nothing shows" meaningless. It restores the demo split **and clears every per-employee exception** at both ends — an interrupted run strands those too, and one stale exception makes "everyone else is untouched" untestable.

### A week-off has two levels, and the employee's overrides the organisation's

Which day somebody does not work is answered at two levels — Settings → Week Off for the organisation ([src/data/weekOff.ts](src/data/weekOff.ts), registered in `ORG_SETTINGS`), and `weekOff` on the employee record for one person. `weekOffOf(employee)` in [src/data/employees.ts](src/data/employees.ts) is that resolution and the only thing that should read either store.

- **There used to be one level.** `weekOffOf` ended `?? 'Sunday'`, which was the organisation's policy in every sense that mattered — it decides which day the attendance grid may leave unworked, which days a leave request is charged for, and which absences payroll deducts — except that no organisation could see it, state it, or change it. A company closed on Friday could only express that by setting a personal week-off on every employee one at a time, and every new joiner silently reverted to Sunday.
- **`WeekOffDay` was three literals** — Sunday, Monday, Tuesday — documented as the days "the organisation rosters its week-offs across". That was true of ModCon Builders' demo roster and of nobody else; the compiler was enforcing one tenant's staffing pattern on every other. It is all seven days now.
- **Absent means "follow the organisation", and that is a state the edit form must be able to return to.** The profile's picker leads with *Follow organisation (Sunday)* naming whatever the policy resolves to, seeds from `emp.weekOff ?? ''` and saves `editWeekOff || undefined`. It used to seed from the *resolved* day and always write it, so opening anyone's profile and saving would pin the current policy onto them as a personal override — and quietly stop them following the next change. `hasOwnWeekOff(employee)` is the test for which level a day came from.
- **Both surfaces that show a week-off say which level it came from** — the profile row reads `Monday · their own` or `Wednesday · organisation's`. A day differing from Settings with nothing to explain it reads as a defect in the roster rather than the arrangement it is; one that merely matches Settings today should not look pinned, because it moves when the policy does. Same reason as the leave balance's "Custom entitlement" badge.
- **Settings names everybody the policy will not reach.** An administrator changing the company's day is entitled to know which people keep their own, rather than discovering it from a roster that disagrees with the policy that supposedly produced it.
- **This one has a fallback where holidays and the salary split have none.** Those show "not set", because a plausible default is indistinguishable from a decision the organisation made. Here nothing is not an option: every date must resolve to worked or not, and an undeclared organisation would otherwise have a seven-day week — marking every Sunday absent for everybody and deducting it from their pay. `FALLBACK_WEEK_OFF` is that day, named rather than inlined, and Settings says the organisation has not chosen rather than presenting it as a choice.
- **Read at call time, never captured at module load**, and anything that stays mounted subscribes with `useWeekOffRevision` — an administrator can change it in Settings, and the cache is hydrated from Firestore after sign-in.
- `tests/e2e/week-off-policy.spec.ts` is the guard, in the org-settings project because it writes shared configuration and restores it. It sets the policy to **Wednesday** on purpose: seeded personal week-offs are Sunday, Monday or Tuesday, so a policy set to one of those would be indistinguishable from the override it is meant to be overridden by. It asserts both directions — somebody with no day of their own moves, somebody with one does not.

### Attendance is geofenced, and the evidence lives where its author cannot reach it

HR draws the places the organisation accepts a check-in from (Settings → Attendance Locations); each check-in and check-out captures a position, is judged against those places, and is filed to Firestore as a stamp **its own author cannot edit**. Full design in [docs/geofenced-attendance-spec.md](docs/geofenced-attendance-spec.md).

- **What it proves and what it cannot is the whole design constraint.** It proves a submitted position lies inside a fence the organisation actually drew, that the moment is the server's, that the stamp was filed by the employee it is about, and that nobody can alter it afterwards — all four in `firestore.rules`, none in the app. It **cannot prove the coordinates are true**: the Geolocation API reports whatever the platform hands it, and on a rooted device that is whatever a mock-location app says. So `falsified` is a human's finding, written by an administrator into a separate field on a stamp that stays byte-identical underneath — never the system's inference. Device attestation via a Cloud Function is the real answer and needs a backend this project does not have; the collection and document shape are already the ones that migration would keep.
- **The stamp is deliberately not part of `AttendanceRecord`.** Attendance records are the localStorage overlay the employee's own browser owns. That is fine for a time somebody typed and useless for evidence somebody may want to falsify — anyone can edit `modcon.hr.attendanceRecords` in devtools. `attendance_stamps` is where the rules can refuse an author their own edit, which is the one property the feature rests on.
- **The fence exists twice, and that is not duplication to tidy away.** The app reads `org_settings/<orgKey>__attendanceGeofence`, whose payload is a JSON *string*; rules have no JSON parser, so that copy is unreadable to them. `attendance_geofences/{orgKey}` is a structured projection written by the same save, read **only** by `firestore.rules`. The app never reads it back, so the two cannot disagree about what the app shows; a stale one fails closed (refusing `inside` claims), and HR fixes it by saving again. An earlier draft had the client send the geometry with each stamp — forge a fence around your sofa and every check-in is "inside". The projection is what closes that.
- **Rules have no `sqrt` and no `cos`,** which is why distance is compared squared and why `metresPerDegreeLng` is stored on each site (derived by the client, range-checked by the rules) rather than computed. `squaredMetresBetween` in [src/data/geofenceRules.ts](src/data/geofenceRules.ts) and `squaredMetres` in `firestore.rules` are mirrors — change them together.
- **A fix's own accuracy is never added to the radius.** A deliberately degraded reading would otherwise enlarge every fence it meets. Accuracy is handled once, before the comparison, by refusing a reading too vague to place anybody.
- **Three modes, and `advisory` is the one that matters.** No organisation knows in advance that its office wifi geolocates 600 m down the road. Advisory captures and judges everything and refuses nobody, so the queue fills with exactly the evidence enforcement would have acted on. `off` is the default for a new organisation — no fence, nothing captured, same reasoning as the unset holiday calendar.
- **Exemptions are load-bearing.** A construction company's site engineers do not work at head office, and a fence that refuses them every morning gets switched off for everybody within a week. An exempt employee's position is *not captured at all*.
- **Signals are heuristics and are never summed into a score** — a score invites a threshold and a threshold invites acting automatically, which is the one thing this must not do. Each carries its own explanation into the queue because a queue of flags nobody can interpret is a queue nobody works.
- `tests/unit/geofenceRules.test.ts` covers the arithmetic and every signal's false positive; `tests/rules/attendance-stamps.rules.test.mjs` is the boundary and the only place it is reachable; `tests/e2e/geofenced-attendance.spec.ts` is the wiring, in the org-settings project because the fence is shared configuration. That spec runs in **one** signed-in context on purpose: check-in is self-only, the personas have no directory record, and the link is written into that context's localStorage — a second context is a browser where the account is nobody. Hence the mutable geolocation stub in `tests/e2e/geolocation.ts` rather than Playwright's `setGeolocation`, which supplies no altitude, speed, heading or timestamp and so cannot exercise the signals at all.

### The holiday calendar is the organisation's, and there is no default one

Which days the company is shut is per-organisation configuration (Settings → Holidays, [src/data/holidays.ts](src/data/holidays.ts), registered in `ORG_SETTINGS`). `getHolidayDirectory()` returns what the organisation declared, or `[]`.

- **There was a hard-coded ten-day India 2026 calendar, in two places.** `defaultHolidays` in `src/data/holidays.ts` was returned to any organisation that had not saved its own, and a second, ungated copy sat exported in [src/data/common.ts](src/data/common.ts) that nothing imported — the more dangerous of the two, since anything that had ever imported it would have shown those days to every tenant. Both are gone; the calendar has one home.
- **A holiday nobody declared is somebody's leave, or their pay.** The attendance calendar treats holidays as non-working, `chargeableLeaveDays` excludes them from what a leave request costs, and payroll deducts unpaid absence from what is left. That is why a plausible default is worse than none here — it is indistinguishable from a decision the organisation made. Same reasoning as the salary structure above.
- **Empty means "nobody has set this up", and every surface says so** rather than rendering a working year with no holidays in it: the calendar page, the Leave module's Holidays tab, and the Settings header all name the consequence ("no day is excluded when leave is charged"). The two dashboards already had an empty state.
- **The year is derived, never a literal.** `holidayYearsCovered(holidays)` backs the calendar page's subtitle and the Settings count, which were the strings `"Complete holiday schedule for 2026"` and `"— FY 2026"` sitting beside a list that can hold any year — two independent claims about the year that had to be updated together, and would not have been. It spans (`2026–2027`) when a calendar crosses a financial year.

### Uploaded payslips

Payslips exist twice, and the difference matters. `buildPayslip` (`src/data/payroll.ts`) **computes** one from CTC and attendance — that is a statement. The PDF payroll actually issued is **uploaded** by an administrator (Payroll → Upload payslips) into the Firestore collection `payslip_documents`, one document per employee per month, id `<orgKey>__<employeeId>__<YYYY-MM>` so a re-upload corrects the month instead of accumulating duplicates. `src/lib/payslipDocuments.ts` holds the module; the employee sees theirs on Finance, where the uploaded PDF outranks the computed statement.

- **The bytes live in the document, base64-encoded**, capped at `PAYSLIP_MAX_BYTES` (720 KB), for exactly the reason the handbook's do: no Cloud Storage bucket is provisioned, and Storage rules cannot read Firestore to check a role. The reasoning and the migration path are in [src/lib/handbookStorage.ts](src/lib/handbookStorage.ts); both features share its `readAsBase64` seam.
- **Reads are per employee, not per org.** `firestore.rules` allows `isOrgAdmin()` or `isSelf(employeeId)` against `employee_links`, so an employee's query *must* filter on `employeeId` as well as `orgId` — a list is evaluated against every document it returns and fails whole otherwise. `tests/rules/payslip-documents.rules.test.mjs` is what proves a colleague cannot read someone else's salary; the E2E suite drives the client and cannot.
- **Bulk upload matches files to people by the employee code in the filename**, and shows the match list before writing anything. Files that match nobody are listed, never dropped — a file silently ignored looks exactly like one successfully uploaded.

### Onboarding

`standardTaskTemplate` in [src/data/onboarding.ts](src/data/onboarding.ts) is cloned per hire. HR and Admin (`full` on the Onboarding module) start one from the page; there was previously **no way to create a record at all**, so the page could only show what the seed contained and every stat card read 0 for an organisation that had hired somebody.

- **"Onboarding In Progress" counts every record under 100%.** It required `progress > 0` as well, so a new hire on day one — the clearest case of one in progress — counted as none.
- Employees already tracked are absent from the picker rather than disabled: a second checklist would split one person's progress across two records.

### Statutory payroll is off until the organisation declares it on

India's provident fund, ESI, professional tax and TDS are computed by [src/data/statutoryRules.ts](src/data/statutoryRules.ts) — pure arithmetic, imports nothing, unit-tested — and switched on per organisation from Settings → Payroll Compliance ([src/data/statutory.ts](src/data/statutory.ts), registered in `ORG_SETTINGS` as `statutoryConfig` and `employeeTaxElections`).

- **The rates ship; the registrations do not.** 12% EPF is the Act, not a company's opinion, so asking each customer to type it in would be asking them to re-derive the law and get it wrong. Whether an *establishment* is covered depends on headcount, state and business — so every scheme is off until an administrator declares it, and an organisation that declares nothing gets exactly the payslip this app produced before the engine existed: gross minus unpaid absence, nothing else. That is the same "no plausible default" rule as the salary split and the holiday calendar, applied to the half of the problem where a default is a wrong answer.
- **`statutory` on `PayslipComponents` is `null`, never a block of zeroes**, and every surface has to tell the two apart: "PF ₹0" reads as a contribution that was calculated and came to nothing; no PF is a company that does not run the scheme.
- **A scheme will not switch on without somewhere to remit to.** `normalizeStatutoryConfig` forces `enabled` false without an establishment code (or a TAN for TDS), and the Settings form refuses before saving rather than letting a toggle silently not stay on. Money deducted with nowhere to send it is worse than money not deducted.
- **Each head computes on its own base** — EPF on the PF-liable wage (Basic), ESI and professional tax on the month's gross, TDS on the projected year. Computing them all from one figure would roughly double every deduction in the country.
- **EPS is capped at ₹15,000 whatever the establishment chooses; EPF may or may not be.** Two ceilings, and they are not the same ceiling: restricting caps the employee's deduction at ₹1,800, contributing on full wages deducts 12% of the whole Basic, and both are lawful. Computing both from one ceiling either under-deducts PF or over-remits to a pension scheme that will refuse it.
- **The EPFO admin-charge floor is the establishment's, not the member's.** `epfContribution` charges the percentage only; `establishmentAdminCharge` applies the ₹75 minimum once. Per member it would multiply by headcount.
- **`employerShareInCtc` is the one setting that changes what somebody is paid**, not what is withheld from it, and it is a declared choice with both options spelled out because both arrangements are ordinary. When the employer's share sits inside the CTC, gross is circular — gross decides Basic, Basic decides the contribution, the contribution decides gross — **and has no exact solution**, because every step rounds and the admin-charge floor is not a percentage of anything. A bare fixed point oscillates. `resolveMonthlyGross` states the rule instead: *the highest gross whose employer cost still fits inside the CTC*, with the unspendable rupee reported as `ctcVariance` rather than absorbed.
- **§87A is a rebate, not a zero band.** Modelled as a band, a rupee over the ceiling costs a few rupees instead of sixty-odd thousand, and that cliff is the law's. The new regime ignores declared deductions rather than allowing them — silently allowing an 80C declaration under a regime that does not permit it under-deducts all year and lands as a demand on the employee.
- **TDS spreads over the months that *remain*, not twelve**, or somebody who joins in October is under-deducted by half; `taxDeductedSoFar` credits what is already withheld so a mid-year raise or regime change corrects the rest of the year instead of restarting.
- **Gratuity qualifies at one year for a fixed-term employee** since the 2025 change, five otherwise, and a part-year over six months counts as a whole one. A payroll written before that change pays nothing to exactly the population it was made for.
- **The Code on Wages floor is a finding, never a correction.** Settings → Salary Structure accepts any Basic percentage, so an organisation can configure itself into under-contributing with nothing saying so; `wageFloorFinding` reports the shortfall and the `statutoryWages` contributions are owed on, and an administrator restructures or contributes on the higher figure. Recomputing everybody's PF on a number the company never agreed to is what this codebase refuses everywhere else.
- **Professional tax is a state levy and the reference schedules are a starting point, not the answer.** Notifications move per state and this app cannot know which is current where a company operates, so slabs are editable and each carries the month it was last checked. Work locations are plain strings with no state on them, so `stateByLocation` maps them in the statutory config rather than migrating the location model; an unmapped location deducts nothing, because another state's slab is simply a wrong deduction.
- **Every rate carries `checkedAgainst` and Settings renders it.** A rate that has moved produces a payslip that looks exactly like a correct one, so the page says how old its figures are.
- **Known gap, stated in the UI:** ESI coverage is decided at the start of each contribution period (April, October) and holds until it ends; this app tests the threshold monthly instead. `esiContribution` takes a `coveredOverride` for when that carries forward.
- **`computeTax` is gone.** It was a simplified slab table, exported, documented as "retained but not applied", called by nothing, and wrong in ways that only mattered once something called it — stale slabs, no rebate, no standard deduction, no cess. A second, worse definition of income tax beside the real one is how a payslip eventually gets computed with the wrong one.
- **One definition of the deduction rows.** `deductionRows` / `employerContributionRows` in [src/data/payroll.ts](src/data/payroll.ts) — three surfaces show them, and three hand-written lists is three chances for one to label ESI as loss of pay. Which had already happened: Finance rendered `otherDeductions` under "Loss of Pay (unpaid absence)" while the loss of pay was in `lossOfPay`, so the row read ₹0 however much absence there was.
- `tests/unit/statutoryRules.test.ts` is where a rate is checked (106 assertions, worked examples with the figure spelled out). `tests/e2e/statutory-payroll.spec.ts` covers what a unit test cannot — that a declaration reaches Firestore and a payslip follows — in the org-settings project, restoring the document at both ends: a statutory configuration left behind does not look like a fake, it looks like an organisation that deducts provident fund.

### Statutory returns: one of them is the filing, the other is not

`npm run test:unit` covers both. [src/data/returnFiles.ts](src/data/returnFiles.ts) holds the formats and imports nothing; `src/data/statutoryReturns.ts` assembles a real month from the directory and `buildPayslipComponents`; Payroll → Statutory returns is the surface.

- **The ECR *is* the filing.** EPFO's Electronic Challan cum Return is a `#~#`-delimited text file uploaded to the employer portal exactly as downloaded. Eleven fields in a fixed order — reordering two numeric columns produces a file that uploads cleanly and remits the wrong amounts to the wrong scheme, which is why the test writes the expected line out literally rather than composing it from the same array.
- **The TDS output is not a return, and the UI says so.** A quarterly salary return is prepared in the department's RPU and validated through the FVU, and what that emits is the file the department accepts. Nothing generated in a browser is that file, and a download labelled "Form 138" that is not a filed return is worse than no download. What is produced is the **deductee-wise schedule that goes into it** — PAN, amount paid, tax withheld, month by month — which is the part payroll knows and the part that is miserable to assemble by hand.
- **A row that cannot be filed is reported, never dropped**, and it matters more here than in any other upload in this app: a member silently missing from an ECR looks exactly like a member who was not employed that month, the contribution is not remitted, nobody notices until they try to withdraw, and §7Q/§14B interest runs from that month. So the file is generated from the rows that *are* usable and everybody excluded is named.
- **The totals are computed from the filed set**, not from the directory, so they reconcile against the challan rather than against the intention.
- **A separator inside a name is stripped, not escaped** — the format has no escape, and twelve fields shifts every column after the name.
- **A member paid nothing is filed with zero wages and flagged**; omitting them reads as somebody who left.
- **A missing PAN is a warning and the deductee stays in** the TDS schedule — the return has to reconcile against the challans actually paid, and §206AA is a decision for whoever files, not something to resolve by omission.
- **Returns are built from what payroll computes now, not from a stored payslip.** A stored payslip records what was *paid*; a return states what is *owed* under today's configuration. When they disagree the return should carry the corrected figure and the difference should be visible.
- **NCP days are the same unpaid-absence figure payroll deducted for.** A separate count that could disagree with the payslip is how a return stops reconciling against the salary it came from.

### The trial is a rules property, and the lock is not

[src/data/subscriptionRules.ts](src/data/subscriptionRules.ts) is the state machine (pure, unit-tested); [src/lib/subscription.ts](src/lib/subscription.ts) is the storage; Organizations → Subscriptions is the super admin's console and Settings → Billing is the tenant's.

- **The subscription lives on `organizations/{orgId}`, which is tenant-readable and super-admin-writable.** That single fact is the whole model: an organisation cannot extend its own trial, mark itself paid, or comp itself, however much of the client it rewrites. `tests/rules/subscription.rules.test.mjs` asserts it rather than assuming it.
- **The lock is a commercial gate and explicitly not a security boundary.** The rules do not deny reads to an unpaid tenant and must not: a company locked out of its own employee records over an invoice loses its attendance history, and no HR product should have that lever. `LOCKED_CAPABILITIES` names what actually stops — payroll, the directory, approvals, settings, recruitment — and reading, plus anybody's own data, is never blocked. Somebody determined could keep working past a trial with devtools; that is a billing problem, not a breach.
- **It fails open.** A missing, unreadable or malformed record resolves to `active`. An HR system that locks a company out because a Firestore read failed has done far more damage than a day of unpaid use — payroll still has to run on the 30th.
- **The order the states beat each other in is the logic**: suspension beats everything including a paid term (a payment not yet refunded must not quietly undo a deliberate suspension), an override beats the dates, a paid term beats a trial, then trial → grace → locked.
- **Paid and comped are different fields and different buttons.** A comp recorded as a payment is a comp nobody can find again — and it *will* be looked for again, at renewal, by somebody who was not there. `overrideReason` is required and `overrideBy`/`overrideAt` are stamped.
- **The trial price is stored in paise on the record, not looked up at charge time.** Paise because the point is that the figure can be tiny — a ₹1 trial is `100`, and a rupee float would eventually be `0.01` and round away. Stored because a discounted offer is a promise made on a particular day: somebody who signed up on the ₹1 trial keeps it when the campaign ends.
- **A tenant cannot pay, so it asks.** `subscription_requests` is the tenant's only write in the feature and grants nothing: an org admin creates one with `status` pinned to `open` in the client *and* in the rules, and only a super admin reads them all or closes one. **There is no charge anywhere in this app**, because the only trustworthy signal that money arrived is a signed webhook to a server and this deployment has none — anything a browser reports about a payment is a claim by the party who owes it. `grantPaidTerm` is exactly what a webhook handler would call; when a Cloud Function exists it replaces the human confirmation, not the shape. Settings → Billing says all of this, because a form that looks like a checkout and is not one wastes somebody's afternoon.
- **The countdown banner is quiet for most of a trial** (`QUIET_UNTIL_DAYS`) — a nag from day fourteen is furniture by the time it matters — and **an employee is never shown their employer's trial**, only the lock notice, which they can otherwise do nothing about but reasonably read as their job being at risk.
- **`useSubscription` recomputes on a timer as well as on a snapshot**: what turns a trial into a grace period is the clock, and nothing writes to Firestore at midnight.

### An employee's entitlement can differ from the organisation's policy

Settings → Leave Policies says what the company grants; it could not say what was agreed with one person. HR uploads those exceptions as a CSV (Settings → Leave Policies → "Custom entitlements for individual employees"), stored as a sparse map of employee id → leave type → override in `ORG_SETTINGS.employeeLeavePolicies`, beside the policy list and under the **same change event** — every surface that re-renders when the organisation's quota moves has to re-render when an individual's does.

- **`getLeavePoliciesFor(employeeId)` is what entitlement is derived through**, and `getApplicableEntitlements` asks it per employee rather than once per page: two people on the Leave module's team view can legitimately be on different entitlements for the same type. Called with no id it is exactly `getLeavePolicies()`. Every balance in the app — Leave, Dashboard, the profile's Time Off tab, the Apply Leave check — already ran through that one function, so nothing else needed changing.
- **The override is sparse at both levels, and deliberately narrow.** Only how many days (`annual` *or* `monthlyAccrual`) and when they start (`minTenureMonths`). Carry-forward, encashment and half-day stay the organisation's policy for that type — they are not terms of one person's employment — and an employee is never offered a leave *type* the organisation does not grant, so the type list stays the organisation's. A full policy copy per person would freeze all of it at upload time, and the next change in Settings would silently miss everyone with an exception.
- **A monthly policy's yearly figure stays derived** (`monthlyAccrual * 12`), the same invariant `normalizePolicy` keeps, so an exception cannot store an annual figure that disagrees with the accrual.
- **A row setting the wrong figure for how the type accrues is refused, not converted.** Twelve days a year against Casual (a day a month) would have this app inventing an accrual pattern nobody typed, and twelve days available in April is not the same promise as one a month. `parseEmployeeLeavePolicyCsv` **reports** every row it cannot use rather than dropping it — a line silently ignored looks exactly like a line applied, and the person it named keeps accruing on the organisation's quota.
- **The upload merges at both levels**: a file about three people is a statement about those three, and a row about their Earned Leave says nothing about the Casual exception they already have. Removing an exception puts the employee back on the organisation's policy, never on nothing.
- **Both surfaces that show the figures say when they are somebody's own** — a "Custom entitlement" badge on the Leave balance card and on the profile's Time Off tab. An unexplained difference from Settings reads as a defect in the accrual rather than as the exception it is.
- The section heading avoids the words "leave policies" on purpose: Playwright matches an accessible name by substring, and a second heading containing that phrase would make the section above it ambiguous. `tests/e2e/employee-leave-policy.spec.ts` is the guard, in the org-settings project because it writes shared configuration; it walks the figure from the upload to the organisation's Firestore copy to the employee's own balance card, and restores the document's pre-run snapshot — a fake entitlement left behind is not visible as a fake, it simply looks like the balance.

### Deciding leave — two routes to authority, and seeing a request is neither

`getVisibleEmployeeIds` answers whose records you may read; `getApprovableEmployeeIds` ([src/lib/dataScope.ts](src/lib/dataScope.ts)) answers whose leave you may decide, and they are deliberately different sets.

**Authority comes from a position in the reporting tree *or* from the administrator role, and either alone is enough.** Whoever an employee reports to decides their leave, as does anyone further up that same line; and **HR and Admin decide organisation-wide**. `Employee` decides nothing whatever the org chart says, because the Leave module is self-service at that permission level.

- **HR is a standing alternative, not a fallback that unlocks once the manager is missing.** Making it conditional would mean the answer to "can HR decide this?" differs per employee for reasons nothing on the page explains, and an escalation route that appears only after the data is already broken is one nobody finds in time. HR's set is the whole directory however complete the org chart is.
- **This replaced a tree-position-only rule, and that rule was wrong in the other direction.** Under it an administrator decided nothing — an admin sits nowhere in an org chart — and an employee with no `reportingManagerId` was undecidable: the request sat pending until somebody edited the org chart. The correction runs the opposite way from the original defect, so **a change here has to be checked against both** — the queue that was once the whole company for everybody, and the queue that was later empty for the account an organisation administers itself with (`src/lib/organizations.ts` provisions the first account as `hr`, so that is the same account).
- **Nobody approves their own request at any level**, `self` being removed from whichever set the role produced. An HR Manager's own leave goes up their own reporting line, or to another administrator.
- **A missing reporting manager is still worth fixing, just no longer fatal.** Every request from a manager-less employee now lands on HR rather than on somebody who knows the team, which is why the profile's Reporting Manager row keeps an always-visible button rather than a hover pencil (`ReportingManagerRow` in [src/pages/employees/index.tsx](src/pages/employees/index.tsx)).

- **The queue used to be the whole company, for everyone who could open the page.** `/dashboard/pending-approvals/leave-requests` filtered on `status === 'Pending'` and nothing else, so a team lead was offered Approve on other departments' leave, on their own manager's, and on their own — and the button worked.
- **A Manager matching no employee record decides nothing**: no record means no place in the tree, so the answer is nobody rather than everyone — the direction a missing answer has to fail — and the page says that is why it is empty rather than leaving a blank list to be read as "nothing pending". **HR and Admin are exempt from that**, their authority being the role an administrator granted rather than a row in a client-editable directory; telling them to go and link an account would send them to fix something that changes nothing they can decide, so the page says the organisation has nothing pending instead.
- **`updateLeaveRequestStatus` is the enforcement point, not the pages.** Leave requests are a localStorage overlay with no server behind them, so there is no second copy of this rule; putting the check in the one function that writes a status is what stops a fourth approval surface from skipping it. The deciding `profile` is a **required** argument for that reason — optional, every existing call site would have kept compiling and kept approving everyone. As with the recruitment overlay, the client check is the whole gate there: a property of where these records live, not a lighter permission.
- **It returns `{ ok }`, and a refusal is shown.** The buttons are already hidden where authority is absent, so reaching a refusal means the UI and the rule disagree, and silence would look exactly like a decision that landed.
- **`pendingApprovalsSummary(profile)` scopes the Leave Requests count to the same set**, or the card promises twelve approvals and the queue behind it holds two. For HR and Admin that scoped figure *is* the organisation's — the scoping is not being skipped, it is what organisation-wide adds up to. The other three rows are still organisation-wide for everyone — the same gap in a different workflow, left alone rather than changed on the way past.
- `tests/e2e/leave-approval-scope.spec.ts` is the guard, in the role projects (Chromium, once per persona — this is app logic, not engine behaviour). It seeds a reporting line into `modcon.hr.customEmployees` and `modcon.hr.leaveRequests` directly, because the personas match no employee record and a Manager has `view` on Employee Directory, so no persona can hire its own reports through the UI. **Its seeded outsider carries `reportingManagerId: null` on purpose** — that one record is both "outside the manager's line" and "has no line at all", so the same row proves the manager is scoped out and the administrator is not. **One of its tests signs in as `HR_PERSONA` and runs only from the manager project** — HR is nobody's role project, and it decides in its own browser context so its approval cannot empty the queue the manager's test needs.

### Employee documents

The documents filed against an employee live in the Firestore collection `employee_documents` (`src/lib/employeeDocuments.ts`), one document per name per person, id `<orgKey>__<employeeId>__<slug>` so re-filing replaces rather than duplicates. Metadata only — a name, a type, a status — never the file.

- **Who may file which kind is a rule, and rules need a server.** Primary documents (Aadhaar, PAN, bank details) are filed by the employee themselves or by HR; secondary documents — the organisation's paperwork — by an administrator or HR. This lived in localStorage with the check in the page, which meant anyone who restored the hidden button could file anything. `firestore.rules` states it again and that copy is the one that decides.
- **Which kind a document is follows from its *name*, never a stored field** — a category on the document would be a claim the writer makes about their own write. The list is matched exactly in both places (`PRIMARY_DOCUMENT_NAMES` and `isPrimaryDocumentName`); a substring test would catch "Aadhaar Card Verification Note", which is the company's paperwork and somebody else's job to file.
- **A filed document always arrives `Pending`, including a re-file**, or an employee re-files their own PAN card as `Verified` and has verified themselves. Verifying is `isAdmin()`, and it may not change the name or the employee — otherwise "verify" is a rename, and a rename across the primary boundary undoes the whole rule.
- **`isSelf()` needs `employee_links/{uid}`, and both hiring orders now write it.** Admin → Create account links the new account to an employee record already carrying the address (`src/lib/accountInvites.ts`); Employees → Add Employee links an account that already exists (`linkAccountForEmployee` in `src/data/employeeLinks.ts`). Only the first half existed, so anyone hired in the other order stayed unlinked and read none of their own salary or leave — failing closed, silently, on the ordinary path. Both are conservative in the same way: exactly one account in this organisation carrying the address, never over a link that already points elsewhere; anything else is reported for a human. The identity backfill (Settings → Database) remains for records that predate this.
- `tests/rules/employee-documents.rules.test.mjs` is the enforcement test. `tests/e2e/document-upload-access.spec.ts` is the UI half and can only ever prove what the client chose to do.

### Candidates applying — the careers page

`/careers/:orgKey` and `/careers/:orgKey/:jobId` ([src/pages/careers](src/pages/careers/index.tsx)) are **public routes**, outside `AppLayout` and outside `RequireAuth`. They are the only pages read by somebody who does not work here and cannot be given an account before they are hired, and the `job_applications` create rule is **the only unauthenticated write in `firestore.rules`**.

- **A job opening is local until it is published.** Recruitment keeps openings in the localStorage overlay (`src/data/recruitment.ts`), so a role posted in one browser exists in that browser alone — useless to a candidate. `publishJobOpening` ([src/lib/publishedJobs.ts](src/lib/publishedJobs.ts)) copies it into the Firestore `jobs` collection, which is what the careers page reads. Publishing is an explicit act with its own button, not a side effect of posting: `Draft` is a status this app has, and a board that published everything typed into it would put drafts on the internet. The job detail modal says which state a role is in, because "nobody has applied yet" and "nobody could have" look identical otherwise.
- **Open roles are world-readable, and only Open ones.** `jobs` read is `(isSignedIn() && inMyOrg()) || resource.data.get('status','') == 'Open'`. A list is evaluated per document, so an unauthenticated query **must** filter on both `orgId` and `status` or it is denied whole. `.get('status','')` not `.status` — a missing field errors, and an error denies the whole rule including the signed-in clause beside it.
- **What keeps the public write safe is its size, not authentication.** One shape of document (`hasAll` + `hasOnly`), only against a job that org published as Open, at a document id **recomputed in the rules** as `<orgKey>__<jobId>__<lowercased email>`, with `stage` pinned to `Applied` and `source` to `Website`, and **no read granted at all** — an applicant cannot read back, edit or delete even their own. What it cannot do is rate-limit: rules have no request counter. The deterministic id (one application per address per job) is the only bound; App Check is the real answer and is not provisioned here.
- **Re-applying is refused, not overwritten.** The address is half the document id and therefore guessable, so a public `update` would let anyone replace somebody else's application. `submitJobApplication` turns the resulting `permission-denied` into "you may have already applied", rather than swallowing it.
- **Two doors, one collection.** The Apply button inside Recruitment writes the same record with `source: 'Internal'` and `submittedByUid`; the rules let the unauthenticated path write only `'Website'` and the signed-in path only `'Internal'`. Splitting internal mobility into a parallel object is how one of the two lists stops being read.
- **Reads are `isManager()`; advancing is the administrators plus the job's own hiring manager.** The permission matrix gives Manager `view` on Recruitment, so a hiring manager who could open the pipeline and never see anyone in it would be failing closed silently. `isHiringManagerFor(jobId)` resolves `jobs/{jobId}.hiringManagerId` against `myEmployeeId()` — the administrator-authored `employee_links/{uid}`, never the localStorage directory, or anyone could appoint themselves to any shortlist. It additionally requires `isManager()` (a `hiringManagerId` may name an employee-role department head) and that the job is in the caller's org (`emp-*` ids are per-org sequences, so `emp-002` exists in every tenant). Deleting an application is still `isOrgAdmin()`. Advancing is stage-only (`affectedKeys().hasOnly(['stage'])`), or "advance to Interview" doubles as a licence to rewrite the name and the resume.
- **An unlinked account resolves to nobody, and the page says so.** `useMyEmployeeId` ([src/lib/useMyEmployeeId.ts](src/lib/useMyEmployeeId.ts)) reads the same `employee_links` document the rules do, so the UI never offers a button the server will refuse — and the candidate modal always states *why* the controls are absent. "You are not this role's hiring manager" and "nobody has told this app who you are" produce the same empty space, and only one is fixable by the person reading it.
- **The pipeline merges both stores, and both are movable.** `asCandidate` maps an application onto the Kanban next to the recruiter-typed candidates from the overlay; ids are prefixed `application:` so the detail modal knows which store a card came from and `handleStageChange` routes to `setJobApplicationStage` (Firestore) or `updateCandidateStage` (localStorage) accordingly. **For an overlay candidate the client check is the whole gate** — there is no server in that path. That is a property of where those records live, not a lighter permission.
- The resume PDF rides in the document, base64, capped at 720 KB — the same seam and the same reasoning as the handbook and payslip uploads ([src/lib/handbookStorage.ts](src/lib/handbookStorage.ts)).
- **The sign-in page's "See our open roles" link is one organisation's, and it cannot ask which.** It was `/careers`, which resolves to the default organisation, so every tenant's login page advertised ModCon Builders' vacancies. The address in the form cannot answer it either: nobody is signed in, `organizations/{orgId}` is readable only by that tenant, and nothing public maps an email or a domain to one — adding such a map would make tenant membership probeable by anyone. So the link follows `getActiveOrgKey()`, the organisation this browser last signed into, which sign-out deliberately leaves in place; a browser that has never signed in here still gets the default. Guarded in `tests/e2e/interactions.spec.ts`.
- `tests/rules/job-applications.rules.test.mjs` is the enforcement test and the only place the fencing above is reachable — the E2E form only ever submits what the form was built to submit. `tests/e2e/careers.spec.ts` drives the public flow and asserts against Firestore rather than the page, in the `org-settings` project because it writes the organisation's shared data.

### Auth & roles (`src/lib/auth.tsx`)

- Firebase email/password auth. On each sign-in, upserts `users/{uid}` in Firestore with a `role`.
- Roles: `admin | manager | employee`. `ADMIN_EMAILS` are always admin, `MANAGER_EMAILS` always manager; otherwise the Firestore-stored role wins (admins change it from the Admin dashboard), defaulting to `employee`.
- **A role change reaches the session it is about, without a sign-out.** `watchUserProfile` subscribes to `users/{uid}` for the life of the session and republishes `profile`; everything role-dependent already derives from it on each render (the route guards in `App.tsx`, the sidebar's `navItems` filter, `RequireModuleAccess`, `lib/dataScope.ts`), so that one subscription *is* "across the app". It was read once at sign-in and cached, which made every revocation a no-op against the person being revoked — and `applyRoleToExistingAccount` (`src/data/roleAssignments.ts`) exists specifically so that moving somebody out of HR withdraws their administrator access immediately, writing a document nothing read.
  - **Adding a role-changing surface needs no wiring** — write `users/{uid}` and the session follows. `role_assignments` is deliberately *not* watched: it is a grant made before an account exists, and `applyRoleToExistingAccount` mirrors it into `users/{uid}` for accounts that already do, so there is one live signal rather than two that can disagree.
  - **The hard-coded allow-lists still win on the live path**, exactly as at sign-in; otherwise an edit to a fixed admin's document would demote them in the running app and the next sign-in would silently undo it.
  - **`orgId` moving is a reload, not a re-render** (Organizations → "Set HR admin" writes `role` and `orgId` together). The `src/data/*` overlay reads its org namespace at module-load time, so applying it in place would leave one organisation's local data on screen under another's identity — the same reason and remedy as the sign-in path.
  - `tests/e2e/role-change-propagation.spec.ts` is the guard, in the org-settings project. It runs **two live sessions** — an administrator drives the real dashboard control while the subject watches — and never reloads, because a reload re-runs the sign-in upsert and would pass against the old code. Note the trap it documents: an emulator write made with the `Bearer owner` bypass never reaches the app's Watch streams, so a version of this spec that PATCHed `users/{uid}` over REST failed regardless of the client, looking exactly like a broken listener.
- `useAuth()` exposes `profile`, `isAdmin`, and `isManager` (**manager includes admin**). Prefer `isManager` for approval/team gating and `isAdmin` for admin-only.
- E2E test emails are granted elevated roles **only** when built with `VITE_ENABLE_E2E_ACCOUNTS=true`; production builds never trust them.
- **Appointing an employee to an HR designation grants them the `hr` role** (= administrator for that organisation); removing it revokes. Which job titles count is `hrDesignations` on the company profile (Settings → Company Profile) — matched exactly, never by looking for "HR" inside a title, which would catch unrelated roles like "Threat Analyst". **Both the title and the department have to agree**: `carriesHrFunction` in [src/data/companyProfile.ts](src/data/companyProfile.ts) is `isHrDepartment(department) && isHrDesignation(designation)`, and it is what the grant (`src/data/roleAssignments.ts`) and the visibility (`src/lib/dataScope.ts`) both call, so access and visibility cannot disagree about who HR is. A title is not unique to a department — the picker used to offer every title in the company, so "Application Developer" could be nominated and that engineer would have read every salary in the organisation. The picker now offers only titles held in `HR_DEPARTMENT`, keeping already-nominated ones listed so a bad one can be unticked rather than hidden while still stored. Renaming that department stops the grant rather than misdirecting it — fail-closed is the only safe direction here, and the section says so when nobody is recorded in it.
- **There is no self-registration.** An account created that way carried no `orgId`, and "no orgId" used to resolve to the default organisation — so anyone who signed up read the incumbent tenant's data. Accounts are created by an administrator: Admin dashboard → **Create account** (`src/lib/accountInvites.ts`), which stamps the inviter's `orgId` at creation, links the new account to its employee record when exactly one in that org carries the address, and never grants `admin`. `firestore.rules` requires the stamp, so an administrator cannot create an account belonging to nobody either.
- **An account with no `orgId` is *unassigned*, not default.** `myOrgKey()` resolves it to a sentinel matching nothing; super admins are the exemption. A *document* with no `orgId` still reads as the default org (`orgKeyOf`) — that is legacy data, which is a different thing from a stranger. **The identity backfill must run before that rule reaches an organisation**, or its accounts are locked out.
- **An organisation's first account is provisioned as `hr`, not `admin`** (`src/lib/organizations.ts`). It administers that one organisation and cannot grant the Admin role or reach another org. The `Organization` schema still calls the field `adminEmail`/`adminUid` — the name predates the role, and renaming it would be a data migration.
- **Attaching an *existing* account to an organisation** is Organizations → "Set HR admin" (super-admin only). It writes `role: 'hr'` and `orgId` together and repoints the org record. The Admin dashboard can change a role but never an `orgId`, so this is the only path for it.
- **Organisations created before that change still hold a platform `admin` account.** Organizations → "Review admin roles" lists them and converts them, super-admin only. It is a two-stage dry-run/confirm because it revokes Admin from live accounts, and it never touches super admins or the fixed `ADMIN_EMAILS` (whose role is re-asserted at sign-in anyway).
- **The grant is not derived from the employee record at sign-in.** `src/data/employees.ts` is localStorage-backed and therefore client-controlled, so trusting it would let anyone edit their own designation and become an admin. Instead an administrator writes a `role_assignments/{email}` document (`src/data/roleAssignments.ts`) and `firestore.rules` verifies the sign-in self-write against it. `admin` is never assignable this way, in the client *and* the rules.

### Routing & access control (`src/App.tsx`)

- Every page is `React.lazy`-loaded under one `<Suspense>`, and the whole tree is wrapped in `ErrorBoundary`.
- Route guards: `RequireAuth`, `RequireManager` (`/approvals`, `/dashboard/pending-approvals/*`), `RequireAdmin` (`/admin`). Unauthorized users are redirected to `/`.
- The sidebar is data-driven from `src/lib/nav.ts` (`navItems` with `adminOnly` / `managerOnly` flags); `Sidebar` filters by role. **When adding a gated page, update both the route guard in `App.tsx` and the nav flag in `nav.ts`** or the two will disagree.

### Firebase & security rules

- `src/lib/firebase.ts` holds the public web config for project `modcon-hr` (safe to ship). Firestore uses long-polling only on localhost.
- `firestore.rules`: helpers `isSignedIn` / `isAdmin` / `isManager` / `isOrgAdmin`, plus the tenant helpers `orgKeyOf` / `myOrgKey` / `inMyOrg` / `writingToMyOrg`. General pattern — read: any signed-in user **of the owning organisation**; write: org administrators per collection. Every tenant document carries `orgId`, and **every query must filter on it**: a list is evaluated against each document it returns and fails whole if one belongs to another tenant, so an unfiltered read is denied, not merely wasteful.
- **A rule that reads `resource.data` denies a `get` on a document that does not exist** — `resource` is null and the dereference fails evaluation. Collections the app subscribes to before anything is written (`org_settings`) must test the document id instead.
- Rules changes must be deployed separately (see Commands); pushing app code does not update them. **The E2E suite runs against live Firebase, so it exercises the *deployed* ruleset, not the working tree** — a rules change cannot be verified end-to-end before it ships, which is what `tests/rules/` is for.
- Tenant isolation as a whole — the invariants, what a deployment can and cannot contain, and the conformance rules for new collections/queries/operations — is [docs/tenant-isolation-spec.md](docs/tenant-isolation-spec.md).

### UI & styling — the brand identity is the token sheet

The look is the Modcon HR brand identity kit (the *Modernist* system): flat and architectural, set entirely in **Archivo**, near-mono **Ink #201E1D on Paper #F3F2F2** with one accent — **Signal Red #EC3013** — a visible modular grid, **zero corner radius** and strong 2px rules. Nothing floats and nothing is decorated; alignment and the strength of the dividers do the organising.

- **`tailwind.config.js` is the token sheet, and it is the only place a brand hex is written.** `brand-*` is the Signal Red ramp, `ink-*` the kit's warm neutrals (`ink-50` is Paper, `ink-100` Surface, `ink-900` Ink), `font-sans`/`font-display` are Archivo, and every step of `borderRadius` is `0px`. A component reads `bg-brand-600`, never `#ec3013`.
- **The radius scale is 0 including `full`**, so the several dozen `rounded-full` pills, avatars and toggles already in the tree square off with everything else rather than quietly reintroducing the old look. Leaving the utility classes in place and retuning the scale is deliberate: the alternative is stripping `rounded-*` from ~230 call sites and having the next one added put a corner back.
- **Charts are the exception to "never a literal", and `src/lib/chartTheme.ts` is where that exception lives.** Recharts takes `fill`/`stroke` as strings, not classes, so every chart reads its colours from that module — the categorical `chartSeriesColor(i)` (accent first, then down the ink ramp), `CHART_STATE` for scales that genuinely mean something (present/absent, on track/behind), and `CHART_GRID` / `CHART_AXIS` / `CHART_TOOLTIP_STYLE` / `CHART_TICK_FILL` for the chrome. Eleven pages carried their own indigo-and-violet hexes, which is how the palette survived a brand change intact.
- **The mark is `src/components/ui/BrandMark.tsx`**, not a re-typed SVG. It is an enclosed monogram on a 24 × 24 tile — columns 4 units wide inset 5 from each edge, the accent column stopping at 7.5 so the M reads asymmetric — and the geometry *is* the identity, so a second copy is a second chance to draw it wrong. `BrandLockup` pairs it with the wordmark (MODCON and HR at equal weight — HR is a division of the name, not a suffix); the kit's product rule is that below 20px the wordmark is dropped and the tile stands alone, which is what the Topbar does at mobile widths. `public/favicon.svg` is the same mark, un-rounded, because the OS applies its own mask.
- **Flush left, everywhere** — headings, copy, and the labels inside wide buttons. `.btn-block` is the full-width button and it starts its label at the left padding edge; use it rather than `w-full justify-center`.
- **Status hues are the one place the mono rule is relaxed, and only where the colour carries meaning.** `statusTone(status)` still maps to green/amber/red for approved/pending/rejected — an HR product that cannot tell those apart at a glance is worse, not more on-brand — but they are muted onto the ramps' lightness so nothing outshouts the accent, and anything merely *categorical* (departments, asset types, avatars, the KPI cards) walks the ink ramp instead of claiming a hue.
- Reusable primitives live in `src/components/ui/` (`Card`, `Table`, `Badge`, `Modal`, `StatCard`, `Select`, `Avatar`, …); `.card` / `.input` / `.btn` / `.label` / `.hr` are in `src/index.css`.
- All shared domain types are centralized in `src/types/index.ts`; feature modules import from there.

### Testing layout (`tests/e2e/`)

`playwright.config.ts` builds with `VITE_ENABLE_E2E_ACCOUNTS=true`, passes the persona addresses into the build as `VITE_E2E_*_EMAIL` (so `src/lib/auth.tsx` and `tests/e2e/config.ts` cannot disagree about who a persona is), serves the production build, and runs eight projects: the app specs (`smoke` + `interactions` + `persistence` + `attendance` + `regularizations` + `check-in-out` + `provisioning` + `password-reset` + `no-auto-signin`) once per engine as `app` (Chromium), `app-firefox` and `app-webkit`; `org-settings` (Chromium only); plus `role-employee` / `role-manager` / `role-admin` (each runs the role specs for its persona, in parallel). `global-setup.ts` provisions the Firebase Auth test accounts; personas/credentials are in `tests/e2e/config.ts` and overridable via `E2E_*` env vars.

**`org-settings.spec.ts` does not run by default, and never against the live project by accident.** Its project only exists when `E2E_FIRESTORE_EMULATOR` is set (what `npm run test:e2e:emulator` does) or when someone opts in with `E2E_ORG_SETTINGS_LIVE=true`; otherwise `--project=org-settings` fails with `Project(s) "org-settings" not found`, which is the gate working. Every run of it adds leave policies to the organisation's real configuration and removes them afterwards — and when that cleanup cannot complete (Ctrl-C, refused sign-in, exhausted quota) the fakes stay, offered to every employee in Settings.

**`org-isolation.spec.ts` runs in its own project that `dependencies` on `org-settings`.** `fullyParallel` parallelises across files, so sharing one project only kept the two off different engines — inside it they still ran concurrently. org-isolation asserts the default organisation's salary structure is the demo split, which is exactly what `salary-structure.spec.ts` spends its run changing and restores in its afterAll, so the two contradicted each other on timing alone and the failure looked like a tenant leak. Playwright has no per-project worker count, so the ordering is a dependency edge.

**It also has its own single-engine project — invoke it as `--project=org-settings`, not `--project=app`.** It writes the organisation's shared `org_settings` documents, where the whole policy list lives in one field, so concurrent engines are concurrent whole-document writers; and running it three times over triples the load on a live project with a daily quota. A three-engine run of it exhausted the Firestore quota and surfaced as `429 RESOURCE_EXHAUSTED` on every publish.

**The suite runs against live Firebase, so its daily quota is a real constraint.** Repeated full-matrix runs in one day will exhaust it, and the failures that follow look like app bugs — refused writes, values that "never land". Check with a plain REST read of any document before believing one: a `429 RESOURCE_EXHAUSTED` means wait for the quota to reset, not debug the app.

**A run can be pointed at the Firestore emulator instead, which costs no quota.** `npm run test:e2e:emulator` starts one and runs the `org-settings` project against it; if an emulator is already listening (`firebase emulators:start`), `emulators:exec` will refuse with "port taken" — run Playwright directly instead: `E2E_FIRESTORE_EMULATOR=127.0.0.1:8080 E2E_ORG_SETTINGS_DEPLOYED=true npx playwright test --project=org-settings`. `E2E_FIRESTORE_EMULATOR` builds the bundle with `VITE_FIRESTORE_EMULATOR_HOST` so `src/lib/firebase.ts` calls `connectFirestoreEmulator`, and points the specs' REST helpers (`tests/e2e/firestore.ts`) at the same place. **That invocation emulates Firestore only, and Auth would be live** — which `global-setup.ts` now refuses, because provisioning creates five real accounts on the production project. Set `E2E_AUTH_EMULATOR=127.0.0.1:9099` too (as `npm run test:e2e:emulator` does), or type `E2E_LIVE_AUTH=true` on purpose. An emulator starts with no `users/{uid}` documents and the rules rightly refuse an account that tries to grant itself `admin`, so `global-setup.ts` seeds those profiles through the emulator's `Bearer owner` bypass, `orgId: 'default'` included — without the orgId every org-scoped write is refused as unassigned.

**Anything that faked "today" belongs in `tests/e2e/clock.ts`.** Seeded week-offs are Sunday, Monday or Tuesday, and a record on the subject's own week-off is deliberately never flagged for regularization, so specs anchored on the wall-clock day failed every Monday. `istToday`/`istDay` anchor on the most recent Wednesday–Saturday instead, derived from the real clock rather than a pinned literal.

**The role specs stay on Chromium.** They are the only specs that sign in per persona, so running them once per engine would triple live Firebase Auth traffic to re-test access-control logic that is app code, not engine behaviour. The Chromium project deliberately keeps the bare name `app` so existing `--project=app` invocations still work. Chrome-only launch flags (the proxy `args`, `PW_CHROMIUM_PATH`) are applied per engine — Firefox and WebKit fail to launch on unknown argv, so they must never inherit them.
