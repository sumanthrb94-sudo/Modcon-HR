# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ModCon HR is a modern HRMS single-page app (React + TypeScript + Vite + Tailwind), backed by Firebase (Auth + Firestore) and hosted on Vercel at `modcon-hr.vercel.app`. **Firebase is backend and database only — never the host.** Firebase Hosting is not used and `firebase deploy --only hosting` must not be run.

## Commands

```bash
npm run dev        # Vite dev server → http://localhost:5173
npm run build      # tsc -b && vite build  (type-check is part of the build)
npm run preview    # serve the production build locally
npm run test:e2e   # Playwright E2E (playwright test)
npm run test:rules # Firestore security-rules tests (Firestore emulator; needs Java)
```

- **Type checking is the CI gate, not lint.** `npm run lint` (`eslint .`) is defined but ESLint is **not configured or installed**, so it currently fails. Correctness is enforced by `tsc -b` inside `npm run build` — run the build to type-check.
- **Tests run against emulators, never the live project.** `npm run test:e2e` points the bundle *and* the specs' REST helpers at the Firestore (`:8080`) and Auth (`:9099`) emulators, and [scripts/e2e.sh](scripts/e2e.sh) starts them if nothing is listening. `npm run test:rules` was always emulator-only. **Nothing needs to run against the live project.** The one thing an emulator cannot tell you — whether *production* is running these rules — is answered by `npm run rules:verify`, which fetches the deployed ruleset from the Firebase Rules API and compares it byte-for-byte with `firestore.rules`. It reads no documents and spends no Firestore quota. When it passes, an emulated run covers the deployed rules; when it fails, deploy rather than test live. There is deliberately **no npm script that runs against the live project** — reaching it means typing `E2E_LIVE_FIRESTORE=true` by hand, and it writes the organisation's real data. A live matrix run on 2026-08-03 exhausted the project's daily Firestore quota, which then refused every read and write for the rest of the day — the app stopped saving, and four fake `E2E Isolation Leave` policies were stranded in Settings for every employee to see, un-removable because removing them needed the quota the run had spent.
- **Single E2E test / project:** `npx playwright test tests/e2e/smoke.spec.ts`, filter with `-g "test name"`, or one role with `--project=role-admin`. Point at the sandbox browser with `PW_CHROMIUM_PATH=/opt/pw-browsers/chromium` (Chromium only — the other engines use their own downloaded builds). The suite builds + serves the production bundle and signs in against the **Auth emulator**, so it needs no network access to Firebase and no live credentials.
- **The app specs run on all three engines; scope with `E2E_BROWSERS`.** `E2E_BROWSERS=chromium npm run test:e2e` is the fast Chromium-only run. Firefox/WebKit need their browsers downloaded once via `npx playwright install firefox webkit`.
- **Security rules are tested separately from the app.** `tests/rules/` runs `firestore.rules` against the Firestore emulator via `@firebase/rules-unit-testing` (`npm run test:rules`, wrapped in `firebase emulators:exec`; needs a JDK). The E2E suite drives the UI and never exercises the rules, so role/permission changes need a test here as well. Each test reseeds — the suites mutate roles, so shared state produces false passes.
- **CI:** `.github/workflows/ci.yml` runs the build and the rules tests on every pull request and push to `main`. E2E is *not* in CI — historically because it needed live Firebase credentials. That reason is gone now that both Firestore and Auth are emulated, so adding it is a scheduling/runtime decision rather than a credentials one; it still has to install browsers and start two emulators.
- **Deploy:** the app ships via **Vercel's Git integration** — pushes to `main` build and promote to production, pull requests get preview URLs. There is no deploy workflow in this repo; build settings live in `vercel.json`. Manual deploy from a checkout: `npx vercel --prod`. Firestore rules deploy separately through Firebase: `npm run rules:deploy` (`firebase deploy --only firestore:rules`). **App code and rules deploy independently — if a change needs both, deploy the rules first or privileged users get permission-denied against the new UI.**

Path alias: `@/*` → `src/*` (configured in both `tsconfig.json` and `vite.config.ts`).

## Architecture

### Mutable collections must persist

Anything a user can change goes through `persistentCollection` in `src/data/persistence.ts` — an org-scoped localStorage store with a change event. **Read it through the store's getter everywhere, never the exported seed array.** Aggregates (`src/data/dashboard.ts`, `src/data/notifications.ts`) and the approval pages all derived from the seeds, so a decision made on one page left every other surface reporting its original figure. `src/lib/seed.ts` is the deliberate exception — it pushes the canonical demo dataset into Firestore. Components that stay mounted while data changes elsewhere subscribe via `useDashboardDataRevision` / `useCollectionRevision`. Seeding `useState` straight from a `src/data/*.ts` array means every edit is lost on refresh, which is what attendance, assets, expenses, helpdesk and payroll all did. `tests/e2e/persistence.spec.ts` guards this: it creates a record, **reloads**, and asserts it survived. The other specs never reload, so in-memory state passes them exactly as persisted state would.

### Four data sources — do not conflate them

1. **Mock/seed data in `src/data/*.ts`** powers most feature pages (attendance, leave, payroll, etc.). It is static seed data, not Firestore.
2. **The employee directory is a mutable localStorage-backed overlay.** `getEmployeeDirectory()` (`src/data/employees.ts`) merges seed employees + locally-added employees minus locally-deleted IDs (both persisted in localStorage). `addEmployeeToDirectory` / `deleteEmployeeFromDirectory` mutate it and dispatch a `modcon-hr-directory-changed` window event; components (e.g. `Topbar`) listen and re-render. So `employees` / `getEmployee(id)` reflect live local edits, **not** the raw seed array.
3. **A separate live Firestore layer** (`src/lib/db.ts` typed collection refs + `src/lib/useFirestore.ts` real-time `use*()` hooks like `useEmployees`, `useExpenses`). This is currently used mainly by the **Admin dashboard**. `useEmployees()` (Firestore) and `@/data/employees` (mock directory) are two different employee sources — pick deliberately.
4. **Organisation configuration is Firestore-backed, and localStorage is its cache.** Leave policies, company profile, holidays, departments, work locations, the salary structure, the permission matrix and the notification/integration preferences live in `org_settings` (one document per setting per org, keyed `<orgKey>__<setting>`). `src/lib/orgSettings.ts` holds the registry, publishes on save, and subscribes at sign-in to hydrate the same localStorage keys the data modules already read synchronously at module-load time. **A new configuration surface goes in that registry, not in a bare localStorage key** — held locally it is invisible to the organisation's other administrators, and leave accrual is what payroll deductions are computed from. See [docs/tenant-isolation-spec.md](docs/tenant-isolation-spec.md) §3.4.

### Departments and locations are both org configuration

Add Employee offers "+ Add new…" for each, and both land in `org_settings` so the next administrator is offered them too. HR can do this — `Employee Directory` is `full` for HR Manager in the permission matrix, and `org_settings` writes need `isOrgAdmin()`, which HR is.

- **Locations were derived, and that read as working.** `syncDirectorySnapshots` collected the distinct `location` of everyone in the directory, so typing a new one and saving made it appear — in that browser only, because the directory is localStorage, and only until its last occupant moved. An office is not a property of the people in it. Declared locations now live in `ORG_SETTINGS.customLocations` ([src/data/locations.ts](src/data/locations.ts)) and the list the app shows is `mergeLocations(derived)` — declared ∪ where people actually are, so nothing needed migrating.
- **Both creation points declare it**: `ensureLocation` in Add Employee and `createLocation` on the profile's inline editor. Adding one without declaring it is the old behaviour, silently.
- **Reporting manager is the live directory** (`employeeOptions={employeeList}`), so somebody hired a moment ago is selectable as a manager immediately. There is no "add a manager" affordance by design: a manager is an employee, and inventing one from this form would create a second person from a form meant for one.
- **Settings → Locations manages them.** Declared locations can be renamed — which moves everyone posted there with them, or they would sit at a name the organisation no longer offers — or withdrawn, but only once nobody is there. Inferred locations (a place that exists only because somebody's record says so) get no buttons: there is no declaration to edit, and they stop being offered on their own when the last person moves.
- `tests/e2e/location-directory.spec.ts` is the guard, in the org-settings project because it writes shared configuration. It asserts against the organisation's Firestore copy and then from a **second browser context** — a reload proves nothing here, since the cache reloads with it, and that second context is also a browser where nobody is posted at the new location.

### The salary split is the organisation's, not the platform's

How a monthly gross becomes Basic, HRA, Medical Allowance, Conveyance Allowance and Special Allowance is per-organisation configuration (Settings → Salary Structure, [src/data/salaryStructure.ts](src/data/salaryStructure.ts), registered in `ORG_SETTINGS`).

- **There is no platform default, and an unset structure shows nothing.** `getSalaryStructure()` returns `null` for an organisation that has not configured one, `buildPayslipComponents` reports `splitConfigured: false` with every component at zero, and each surface renders "not set" instead of a breakdown. Falling back to a plausible Basic 50% would tell a company its pay is divided in a way nobody there decided. Basic 50 / HRA 25 / ₹1,492 is **ModCon Builders' demo data**, gated by `isMockDataCleared()` exactly like `demoCompanyProfile` — the demo org shows it, a real organisation created later does not.
- **Gross and net never depend on the split.** `grossEarnings` is CTC ÷ 12 and net is that minus unpaid absence, so an unconfigured organisation still sees correct pay; only the component rows are withheld.

- **`splitMonthlyGross(monthly, structure)` is the one definition of the arithmetic.** `buildPayslipComponents` computes payslips with it and the Settings preview shows an unsaved change with it; written twice, the preview would eventually promise a split the payslip does not pay.
- **Special Allowance is never configured — it is the remainder**, so the components always sum to the monthly gross including the rupee or two that rounding Basic and HRA leaves behind. The flat allowances are capped by what is left after the percentages, or a low enough salary yields a negative Special Allowance.
- **Read it through `getSalaryStructure()` at call time**, never captured at module load, and subscribe with `useSalaryStructureRevision` in anything that stays mounted — an administrator can change it in Settings, and the cache is hydrated from Firestore after sign-in.
- **Every salary-split assertion lives in `tests/e2e/salary-structure.spec.ts`**, one `describe.serial` in the org-settings project. Two spec files would run in different workers against one emulator and each would see the other's half-applied state — which is exactly what makes "clear it, then check nothing shows" meaningless. It restores the demo split at the end; skipping that changes every payslip in the deployment.

### Uploaded payslips

Payslips exist twice, and the difference matters. `buildPayslip` (`src/data/payroll.ts`) **computes** one from CTC and attendance — that is a statement. The PDF payroll actually issued is **uploaded** by an administrator (Payroll → Upload payslips) into the Firestore collection `payslip_documents`, one document per employee per month, id `<orgKey>__<employeeId>__<YYYY-MM>` so a re-upload corrects the month instead of accumulating duplicates. `src/lib/payslipDocuments.ts` holds the module; the employee sees theirs on Finance, where the uploaded PDF outranks the computed statement.

- **The bytes live in the document, base64-encoded**, capped at `PAYSLIP_MAX_BYTES` (720 KB), for exactly the reason the handbook's do: no Cloud Storage bucket is provisioned, and Storage rules cannot read Firestore to check a role. The reasoning and the migration path are in [src/lib/handbookStorage.ts](src/lib/handbookStorage.ts); both features share its `readAsBase64` seam.
- **Reads are per employee, not per org.** `firestore.rules` allows `isOrgAdmin()` or `isSelf(employeeId)` against `employee_links`, so an employee's query *must* filter on `employeeId` as well as `orgId` — a list is evaluated against every document it returns and fails whole otherwise. `tests/rules/payslip-documents.rules.test.mjs` is what proves a colleague cannot read someone else's salary; the E2E suite drives the client and cannot.
- **Bulk upload matches files to people by the employee code in the filename**, and shows the match list before writing anything. Files that match nobody are listed, never dropped — a file silently ignored looks exactly like one successfully uploaded.

### Onboarding

`standardTaskTemplate` in [src/data/onboarding.ts](src/data/onboarding.ts) is cloned per hire. HR and Admin (`full` on the Onboarding module) start one from the page; there was previously **no way to create a record at all**, so the page could only show what the seed contained and every stat card read 0 for an organisation that had hired somebody.

- **"Onboarding In Progress" counts every record under 100%.** It required `progress > 0` as well, so a new hire on day one — the clearest case of one in progress — counted as none.
- Employees already tracked are absent from the picker rather than disabled: a second checklist would split one person's progress across two records.

### Deciding leave — seeing a request is not authority over it

`getVisibleEmployeeIds` answers whose records you may read; `getApprovableEmployeeIds` ([src/lib/dataScope.ts](src/lib/dataScope.ts)) answers whose leave you may decide, and they are deliberately different sets. A **Manager decides for their subtree only** — everyone beneath them in the reporting tree, however deep. **HR decides for the whole organisation. Admin decides nothing** — an administrator runs the deployment and is nobody's reporting manager, so this is the one scope where Admin is narrower than HR rather than equal to it. `resolveAppRole` is what both the rule and the "why is this empty" copy consult, so they cannot give different accounts of the same page.

- **The queue used to be the whole company, for everyone who could open the page.** `/dashboard/pending-approvals/leave-requests` filtered on `status === 'Pending'` and nothing else, so a team lead was offered Approve on other departments' leave, on their own manager's, and on their own — and the button worked.
- **A manager's approval scope excludes three things their view includes**: themselves (their leave goes up, or to HR — a self-approving manager is the only signature their own request ever needs), the HR Manager (in view scope because HR reports up to them; oversight is not authority), and everybody, when the account resolves to no employee record — an unlinked manager approves nobody rather than everybody, and the page says which of those it is.
- **`updateLeaveRequestStatus` is the enforcement point, not the pages.** Leave requests are a localStorage overlay with no server behind them, so there is no second copy of this rule; putting the check in the one function that writes a status is what stops a fourth approval surface from skipping it. The deciding `profile` is a **required** argument for that reason — optional, every existing call site would have kept compiling and kept approving everyone. As with the recruitment overlay, the client check is the whole gate there: a property of where these records live, not a lighter permission.
- **It returns `{ ok }`, and a refusal is shown.** The buttons are already hidden where authority is absent, so reaching a refusal means the UI and the rule disagree, and silence would look exactly like a decision that landed.
- **`pendingApprovalsSummary(profile)` scopes the Leave Requests count to the same set**, or the card promises twelve approvals and the queue behind it holds two. The other three rows are still organisation-wide — the same gap in a different workflow, left alone rather than changed on the way past.
- `tests/e2e/leave-approval-scope.spec.ts` is the guard, in the role projects (Chromium, once per persona — this is app logic, not engine behaviour). It seeds a reporting line into `modcon.hr.customEmployees` and `modcon.hr.leaveRequests` directly, because the personas match no employee record and a Manager has `view` on Employee Directory, so no persona can hire its own reports through the UI.

### Employee documents

The documents filed against an employee live in the Firestore collection `employee_documents` (`src/lib/employeeDocuments.ts`), one document per name per person, id `<orgKey>__<employeeId>__<slug>` so re-filing replaces rather than duplicates. Metadata only — a name, a type, a status — never the file.

- **Who may file which kind is a rule, and rules need a server.** Primary documents (Aadhaar, PAN, bank details) are filed by the employee themselves or by HR; secondary documents — the organisation's paperwork — by an administrator or HR. This lived in localStorage with the check in the page, which meant anyone who restored the hidden button could file anything. `firestore.rules` states it again and that copy is the one that decides.
- **Which kind a document is follows from its *name*, never a stored field** — a category on the document would be a claim the writer makes about their own write. The list is matched exactly in both places (`PRIMARY_DOCUMENT_NAMES` and `isPrimaryDocumentName`); a substring test would catch "Aadhaar Card Verification Note", which is the company's paperwork and somebody else's job to file.
- **A filed document always arrives `Pending`, including a re-file**, or an employee re-files their own PAN card as `Verified` and has verified themselves. Verifying is `isAdmin()`, and it may not change the name or the employee — otherwise "verify" is a rename, and a rename across the primary boundary undoes the whole rule.
- **`isSelf()` needs `employee_links/{uid}`, and both hiring orders now write it.** Admin → Create account links the new account to an employee record already carrying the address (`src/lib/accountInvites.ts`); Employees → Add Employee links an account that already exists (`linkAccountForEmployee` in `src/data/employeeLinks.ts`). Only the first half existed, so anyone hired in the other order stayed unlinked and read none of their own salary or leave — failing closed, silently, on the ordinary path. Both are conservative in the same way: exactly one account in this organisation carrying the address, never over a link that already points elsewhere; anything else is reported for a human. The identity backfill (Settings → Database) remains for records that predate this.
- `tests/rules/employee-documents.rules.test.mjs` is the enforcement test. `tests/e2e/document-upload-access.spec.ts` is the UI half and can only ever prove what the client chose to do.

### Candidates applying — the careers page

`/careers/:orgKey` and `/careers/:orgKey/:jobId` ([src/pages/careers](src/pages/careers/index.tsx)) are **public routes**, outside `AppLayout` and outside `RequireAuth`. They are the only pages read by somebody who does not work here and cannot be given an account before they are hired, and the `job_applications` create rule is **the only unauthenticated write in `firestore.rules`**.

- **A job opening is local until it is published.** Recruitment keeps openings in the localStorage overlay (`src/data/recruitment.ts`), so a role posted in one browser exists in that browser alone — useless to a candidate. `publishJobOpening` ([src/lib/publishedJobs.ts](src/lib/publishedJobs.ts)) copies it into the Firestore `jobs` collection, which is what the careers page reads. Publishing is an explicit act with its own button, not a side effect of posting: `Draft` is a status this app has, and a board that published everything typed into it would put drafts on the internet. The job detail modal says which state a role is in, because "nobody has applied yet" and "nobody could have" look identical otherwise.
- **Open roles are world-readable, and only Open ones.** `jobs` read is `(isSignedIn() && inMyOrg()) || resource.data.get('status','') == 'Open'`. A list is evaluated per document, so an unauthenticated query **must** filter on both `orgId` and `status` or it is denied whole. `.get('status','')` not `.status` — a missing field errors, and an error denies the whole rule including the signed-in clause beside it.
- **What keeps the public write safe is its size, not authentication.** One shape of document (`hasAll` + `hasOnly`), only against a job that org published as Open, at a document id **recomputed in the rules** as `<orgKey>__<jobId>__<lowercased email>`, with `stage` pinned to `Applied` and `source` to `Website`, and **no read granted at all** — an applicant cannot read back, edit or delete even their own. What it cannot do is rate-limit: rules have no request counter. The deterministic id (one application per address per job) is the only bound; App Check is the real answer and is not provisioned here.
- **Re-applying is refused, not overwritten.** The address is half the document id and therefore guessable, so a public `update` would let anyone replace somebody else's application. `submitJobApplication` turns the resulting `permission-denied` into "you may have already applied", rather than swallowing it.
- **Two doors, one collection.** The Apply button inside Recruitment writes the same record with `source: 'Internal'` and `submittedByUid`; the rules let the unauthenticated path write only `'Website'` and the signed-in path only `'Internal'`. Splitting internal mobility into a parallel object is how one of the two lists stops being read.
- **Reads are `isManager()`; advancing is the administrators plus the job's own hiring manager.** The permission matrix gives Manager `view` on Recruitment, so a hiring manager who could open the pipeline and never see anyone in it would be failing closed silently. `isHiringManagerFor(jobId)` resolves `jobs/{jobId}.hiringManagerId` against `myEmployeeId()` — the administrator-authored `employee_links/{uid}`, never the localStorage directory, or anyone could appoint themselves to any shortlist. It additionally requires `isManager()` (a `hiringManagerId` may name an employee-role department head) and that the job is in the caller's org (`emp-*` ids are per-org sequences, so `emp-002` exists in every tenant). Deleting an application is still `isOrgAdmin()`. Advancing is stage-only (`affectedKeys().hasOnly(['stage'])`), or "advance to Interview" doubles as a licence to rewrite the name and the resume.
- **An unlinked account resolves to nobody, and the page says so.** `useMyEmployeeId` ([src/lib/useMyEmployeeId.ts](src/lib/useMyEmployeeId.ts)) reads the same `employee_links` document the rules do, so the UI never offers a button the server will refuse — and the candidate modal always states *why* the controls are absent. "You are not this role's hiring manager" and "nobody has told this app who you are" produce the same empty space, and only one is fixable by the person reading it.
- **The pipeline merges both stores, and both are movable.** `asCandidate` maps an application onto the Kanban next to the recruiter-typed candidates from the overlay; ids are prefixed `application:` so the detail modal knows which store a card came from and `handleStageChange` routes to `setJobApplicationStage` (Firestore) or `updateCandidateStage` (localStorage) accordingly. **For an overlay candidate the client check is the whole gate** — there is no server in that path. That is a property of where those records live, not a lighter permission.
- The resume PDF rides in the document, base64, capped at 720 KB — the same seam and the same reasoning as the handbook and payslip uploads ([src/lib/handbookStorage.ts](src/lib/handbookStorage.ts)).
- `tests/rules/job-applications.rules.test.mjs` is the enforcement test and the only place the fencing above is reachable — the E2E form only ever submits what the form was built to submit. `tests/e2e/careers.spec.ts` drives the public flow and asserts against Firestore rather than the page, in the `org-settings` project because it writes the organisation's shared data.

### Auth & roles (`src/lib/auth.tsx`)

- Firebase email/password auth. On each sign-in, upserts `users/{uid}` in Firestore with a `role`.
- Roles: `admin | manager | employee`. `ADMIN_EMAILS` are always admin, `MANAGER_EMAILS` always manager; otherwise the Firestore-stored role wins (admins change it from the Admin dashboard), defaulting to `employee`.
- `useAuth()` exposes `profile`, `isAdmin`, and `isManager` (**manager includes admin**). Prefer `isManager` for approval/team gating and `isAdmin` for admin-only.
- E2E test emails are granted elevated roles **only** when built with `VITE_ENABLE_E2E_ACCOUNTS=true`; production builds never trust them.
- **Appointing an employee to an HR designation grants them the `hr` role** (= administrator for that organisation); removing it revokes. Which job titles count is `hrDesignations` on the company profile (Settings → Company Profile) — matched exactly, never by looking for "HR" inside a title, which would catch unrelated roles like "Threat Analyst". **Both the title and the department have to agree**: `carriesHrFunction` in [src/data/companyProfile.ts](src/data/companyProfile.ts) is `isHrDepartment(department) && isHrDesignation(designation)`, and it is what the grant (`src/data/roleAssignments.ts`) and the visibility (`src/lib/dataScope.ts`) both call, so access and visibility cannot disagree about who HR is. A title is not unique to a department — the picker used to offer every title in the company, so "Application Developer" could be nominated and that engineer would have read every salary in the organisation. The picker now offers only titles held in `HR_DEPARTMENT`, keeping already-nominated ones listed so a bad one can be unticked rather than hidden while still stored. Renaming that department stops the grant rather than misdirecting it — fail-closed is the only safe direction here, and the section says so when nobody is recorded in it.
- **There is no self-registration.** An account created that way carried no `orgId`, and "no orgId" used to resolve to the default organisation — so anyone who signed up read the incumbent tenant's data. Accounts are created by an administrator: Admin dashboard → **Create account** (`src/lib/accountInvites.ts`), which stamps the inviter's `orgId` at creation, links the new account to its employee record when exactly one in that org carries the address, and never grants `admin`. `firestore.rules` requires the stamp, so an administrator cannot create an account belonging to nobody either.
- **An account with no `orgId` is *unassigned*, not default.** `myOrgKey()` resolves it to a sentinel matching nothing; super admins are the exemption. A *document* with no `orgId` still reads as the default org (`orgKeyOf`) — that is legacy data, which is a different thing from a stranger. **The identity backfill must run before that rule reaches an organisation**, or its accounts are locked out.
- **An organisation's first account is provisioned as `hr`, not `admin`** (`src/lib/organizations.ts`). It administers that one organisation and cannot grant the Admin role or reach another org. The `Organization` schema still calls the field `adminEmail`/`adminUid` — the name predates the role, and renaming it would be a data migration.
- **Attaching an *existing* account to an organisation** is Organizations → "Set HR admin" (super-admin only). It writes `role: 'hr'` and `orgId` together and repoints the org record. The Admin dashboard can change a role but never an `orgId`, so this is the only path for it.
- **Organisations created before that change still hold a platform `admin` account.** Organizations → "Review admin roles" lists them and converts them, super-admin only. It is a two-stage dry-run/confirm because it revokes Admin from live accounts, and it never touches super admins or the fixed `ADMIN_EMAILS` (whose role is re-asserted at sign-in anyway).
- **The grant is not derived from the employee record at sign-in.** `src/data/employees.ts` is localStorage-backed and therefore client-controlled, so trusting it would let anyone edit their own designation and become an admin. Instead an administrator writes a `role_assignments/{email}` document (`src/data/roleAssignments.ts`) and `firestore.rules` verifies the sign-in self-write against it. `admin` is never assignable this way, in the client *and* the rules.

### Routing & access control (`src/App.tsx`)

- Every page is `React.lazy`-loaded under one `<Suspense>`, and the whole tree is wrapped in `ErrorBoundary`.
- Route guards: `RequireAuth`, `RequireManager` (`/approvals`, `/dashboard/pending-approvals/*`), `RequireAdmin` (`/admin`). Unauthorized users are redirected to `/`.
- The sidebar is data-driven from `src/lib/nav.ts` (`navItems` with `adminOnly` / `managerOnly` flags); `Sidebar` filters by role. **When adding a gated page, update both the route guard in `App.tsx` and the nav flag in `nav.ts`** or the two will disagree.

### Firebase & security rules

- `src/lib/firebase.ts` holds the public web config for project `modcon-hr` (safe to ship). Firestore uses long-polling only on localhost.
- `firestore.rules`: helpers `isSignedIn` / `isAdmin` / `isManager` / `isOrgAdmin`, plus the tenant helpers `orgKeyOf` / `myOrgKey` / `inMyOrg` / `writingToMyOrg`. General pattern — read: any signed-in user **of the owning organisation**; write: org administrators per collection. Every tenant document carries `orgId`, and **every query must filter on it**: a list is evaluated against each document it returns and fails whole if one belongs to another tenant, so an unfiltered read is denied, not merely wasteful.
- **A rule that reads `resource.data` denies a `get` on a document that does not exist** — `resource` is null and the dereference fails evaluation. Collections the app subscribes to before anything is written (`org_settings`) must test the document id instead.
- Rules changes must be deployed separately (see Commands); pushing app code does not update them. **The E2E suite runs against live Firebase, so it exercises the *deployed* ruleset, not the working tree** — a rules change cannot be verified end-to-end before it ships, which is what `tests/rules/` is for.
- Tenant isolation as a whole — the invariants, what a deployment can and cannot contain, and the conformance rules for new collections/queries/operations — is [docs/tenant-isolation-spec.md](docs/tenant-isolation-spec.md).

### UI & styling

- Tailwind with a custom semantic palette: `ink-*` (neutrals) and `brand-*` (primary), plus `.card` / `.input` / `.btn` component classes in `src/index.css`.
- Reusable primitives live in `src/components/ui/` (`Card`, `Table`, `Badge`, `Modal`, `StatCard`, `Select`, `Avatar`, …). `statusTone(status)` maps domain status strings to `Badge` tones — reuse it rather than hardcoding colors.
- All shared domain types are centralized in `src/types/index.ts`; feature modules import from there.

### Testing layout (`tests/e2e/`)

`playwright.config.ts` builds with `VITE_ENABLE_E2E_ACCOUNTS=true`, passes the persona addresses into the build as `VITE_E2E_*_EMAIL` (so `src/lib/auth.tsx` and `tests/e2e/config.ts` cannot disagree about who a persona is), serves the production build, and runs eight projects: the app specs (`smoke` + `interactions` + `persistence` + `attendance` + `regularizations` + `check-in-out` + `provisioning` + `password-reset` + `no-auto-signin`) once per engine as `app` (Chromium), `app-firefox` and `app-webkit`; `org-settings` (Chromium only); plus `role-employee` / `role-manager` / `role-admin` (each runs the role specs for its persona, in parallel). `global-setup.ts` provisions the Firebase Auth test accounts; personas/credentials are in `tests/e2e/config.ts` and overridable via `E2E_*` env vars.

**`org-settings.spec.ts` does not run by default, and never against the live project by accident.** Its project only exists when `E2E_FIRESTORE_EMULATOR` is set (what `npm run test:e2e:emulator` does) or when someone opts in with `E2E_ORG_SETTINGS_LIVE=true`; otherwise `--project=org-settings` fails with `Project(s) "org-settings" not found`, which is the gate working. Every run of it adds leave policies to the organisation's real configuration and removes them afterwards — and when that cleanup cannot complete (Ctrl-C, refused sign-in, exhausted quota) the fakes stay, offered to every employee in Settings.

**`org-isolation.spec.ts` runs in its own project that `dependencies` on `org-settings`.** `fullyParallel` parallelises across files, so sharing one project only kept the two off different engines — inside it they still ran concurrently. org-isolation asserts the default organisation's salary structure is the demo split, which is exactly what `salary-structure.spec.ts` spends its run changing and restores in its afterAll, so the two contradicted each other on timing alone and the failure looked like a tenant leak. Playwright has no per-project worker count, so the ordering is a dependency edge.

**It also has its own single-engine project — invoke it as `--project=org-settings`, not `--project=app`.** It writes the organisation's shared `org_settings` documents, where the whole policy list lives in one field, so concurrent engines are concurrent whole-document writers; and running it three times over triples the load on a live project with a daily quota. A three-engine run of it exhausted the Firestore quota and surfaced as `429 RESOURCE_EXHAUSTED` on every publish.

**The suite runs against live Firebase, so its daily quota is a real constraint.** Repeated full-matrix runs in one day will exhaust it, and the failures that follow look like app bugs — refused writes, values that "never land". Check with a plain REST read of any document before believing one: a `429 RESOURCE_EXHAUSTED` means wait for the quota to reset, not debug the app.

**A run can be pointed at the Firestore emulator instead, which costs no quota.** `npm run test:e2e:emulator` starts one and runs the `org-settings` project against it; if an emulator is already listening (`firebase emulators:start`), `emulators:exec` will refuse with "port taken" — run Playwright directly instead: `E2E_FIRESTORE_EMULATOR=127.0.0.1:8080 E2E_ORG_SETTINGS_DEPLOYED=true npx playwright test --project=org-settings`. `E2E_FIRESTORE_EMULATOR` builds the bundle with `VITE_FIRESTORE_EMULATOR_HOST` so `src/lib/firebase.ts` calls `connectFirestoreEmulator`, and points the specs' REST helpers (`tests/e2e/firestore.ts`) at the same place. **That invocation emulates Firestore only, and Auth would be live** — which `global-setup.ts` now refuses, because provisioning creates five real accounts on the production project. Set `E2E_AUTH_EMULATOR=127.0.0.1:9099` too (as `npm run test:e2e:emulator` does), or type `E2E_LIVE_AUTH=true` on purpose. An emulator starts with no `users/{uid}` documents and the rules rightly refuse an account that tries to grant itself `admin`, so `global-setup.ts` seeds those profiles through the emulator's `Bearer owner` bypass, `orgId: 'default'` included — without the orgId every org-scoped write is refused as unassigned.

**Anything that faked "today" belongs in `tests/e2e/clock.ts`.** Seeded week-offs are Sunday, Monday or Tuesday, and a record on the subject's own week-off is deliberately never flagged for regularization, so specs anchored on the wall-clock day failed every Monday. `istToday`/`istDay` anchor on the most recent Wednesday–Saturday instead, derived from the real clock rather than a pinned literal.

**The role specs stay on Chromium.** They are the only specs that sign in per persona, so running them once per engine would triple live Firebase Auth traffic to re-test access-control logic that is app code, not engine behaviour. The Chromium project deliberately keeps the bare name `app` so existing `--project=app` invocations still work. Chrome-only launch flags (the proxy `args`, `PW_CHROMIUM_PATH`) are applied per engine — Firefox and WebKit fail to launch on unknown argv, so they must never inherit them.
